Implementation
- Program checking collects only control number and full name. Exact normalized
  matching, active/approved membership, current disability screening, throttling,
  signed expiring grants, version checks and live member-change invalidation stay.
  The applicant's stored contact/profile is not exposed or prefilled publicly.
- The confirmed application form no longer asks for a duplicate PWD ID number or
  a universal calendar photo. Admin can add a photo through Create Program,
  Requirements, Document upload, with its required/optional setting and instructions.
  Existing file validation, limits, private routes, correction history and human
  eligibility review apply to those configured uploads.
- New submissions retain the configured_program_requirements_v1 evidence policy
  in their server-written source snapshot and start in Eligibility Review (or
  Needs Information for reported changes). They are never labelled Photo Verified
  merely because no calendar photo is required. Readiness diagnostics distinguish
  Not required from Verified, while every configured required item still must pass.
- Older applications without that policy marker keep their existing calendar-photo
  gate, evidence, correction workflow, private files and manual review history.
  The photo queue excludes only new not-required cases; legacy missing-photo cases
  remain visible. Existing source context hashes retain their previous shape.
- Default photo guidance for new unauthorised drafts describes configured evidence.
  Existing published/custom text and historic application snapshots are not rewritten.
- Shared POST-form handling refreshes existing CSRF inputs from Django's current
  same-origin cookie immediately before submit/FormData creation and on return to
  the tab. It supports the configured cookie name. It does not reload the form,
  erase entered values, exempt CSRF, or replay a rejected write. If the cookie is
  inaccessible, the original server-rendered token remains intact.
- Member Directory shows all original registration profile/digital sections inline,
  separately labelled from current member information. Original membership and
  linked-intake permissions still apply, with the existing protected access audit.
- View Applicant displays its submitted declarations, answers, configured documents,
  applicable historical application photo, eligibility action and application history.
  Original registration details, household/profile cards, membership portrait and
  unrelated membership documents are absent. Member record opens the directory.
