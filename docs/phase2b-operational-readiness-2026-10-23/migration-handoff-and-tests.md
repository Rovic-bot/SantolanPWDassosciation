## Exact migration and startup implications

`membership/migrations/0006_association_pending_intake.py` depends on `membership.0005_onsite_profile_capture` and the swappable user model. Membership 0005 in turn depends on `members.0004_onsite_profile_capture` and membership 0004; do not assume an application's database has these applied merely because the files exist.

0006 creates only `RegistrationIntake`, `RegistrationSubmissionContext`, `RegistrationRevision`, `RegistrationAttachment` and `RegistrationAction`, plus their new-table relationships, constraints and index. It includes no data backfill, old-table field change, EWAF dependency or permission assignment. The nullable one-to-one legacy application link is deliberately CHECK-constrained to NULL; category is Association-only. Future handoff needs a separately reviewed additive migration changing the restriction and introducing any approved provenance/state representation. Do not rewrite 0006 or any historical migration to do that.

`scripts/run.ps1` invokes `manage.py runlocal`. Its unchanged guard validates the pending migration graph before opening the website. Membership 0006 is not in the five explicitly fingerprinted Events/EWAF deferrals. **If 0006 is pending, startup stops even with all registration gates off.** The working applied-history state was not inspected here. The guard must not be bypassed through another launcher, fake migration, new allowlist entry or a blanket migrate command.

The prior direct migration test applied/reversed 0006 on three separate disposable instances across earlier runs. It preserved a synthetic legacy row and checked restrictive constraints. Baseline tables were synchronized from models, not built from the working database's migration history. It did not exercise normal migration history recording or post-migrate content-type/permission creation. Those metadata additions need explicit review and tests; defining permissions does not grant them to staff.

MySQL schema DDL must not be treated as a fully reversible application transaction. Plan backup/restore and partial-DDL failure recovery rather than promising that a failed multi-operation migration automatically rolls back every table. No restore/drop/reverse operation on working data is authorized here.
