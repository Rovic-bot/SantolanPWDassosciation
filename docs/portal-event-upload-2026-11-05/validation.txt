Owner-requested portal, event editor, and application retry changes
Validated locally on 5 November 2026.

Authorized behavior

The owner explicitly requested application tracking with the application
reference alone. This supersedes the prior identity gate for this limited
progress view. It does not change identity/disability checks for making a new
application. Anyone with an issued reference can now see the existing limited
progress summary; private profiles, attachments, answers, assessments, scores,
ranks, and internal decision details are excluded. Archived members remain
excluded. Issued references, aliases, legacy retired routes, receipt access,
tracking feature flags, expiry, CSRF, and hashed reference/IP limits remain.

The public program detail page now shows overview/description, assistance type,
application availability, registration/program dates, slots, configured amount
and correction deadline when present, and the eligibility profile. Removed the
purpose/benefit, review/selection instructions, photo instructions, and configured
requirements list requested by the owner. Actual application requirements are
still enforced and displayed while applying. Admin program details are retained.

Event creation and editing share the same builder and primary fields: title,
location, description, start/end dates and times, and optional image. Category,
program linkage, audience, participation, and capacity controls are absent.
Existing image preview/removal is available in the editor. New events are general;
historical category/link/audience/capacity values are preserved and forged hidden
field changes are ignored. Empty old categories no longer block publication or
hide already-published events from the public list/home calendar. Publication,
schedule, cancellation, authorization, protected program terms, version checks,
image controls, immutable history, and source invalidation controls remain.
Edits receive an automatic audit reason without requiring another visible field.
Annual observance publication rules remain unchanged; Specific Events labels
were removed from the current event/observance presentation.

Program application submission now validates in place. Native required-field
checks stop incomplete requests. Server validation returns structured errors;
the browser retains the original form and selected File objects. Successful
submission uses the existing audited service, receipt session and redirect.
Failed connections and expired verification keep the form open; the latter
offers verification in a separate tab. There is no temporary evidence storage
or browser persistent storage. Files remain selected while the page stays open;
manually reloading/leaving the page still clears browser file inputs. The normal
HTML submission fallback remains available without JavaScript.
