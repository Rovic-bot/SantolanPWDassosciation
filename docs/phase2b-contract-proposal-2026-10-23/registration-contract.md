# Phase 2B registration contract — proposal v1

2026-10-23. **All new schema, codes, permissions, formats and security parameters below are proposals.** Confirmed source rules are identified separately. No approval has been inferred. Decision IDs D01–D14 refer to the [approval register](approval-register.md); they supplement, never replace, IQ/OQ/DEC identifiers.

## 1. Scope and reuse

Deliver two clearly separated pending registration categories: **Association Membership** and **Association-side PDAO PWD ID Assistance**. Online, printed and walk-in channels use the applicable approved requirements. Staff retrieve records in Members; receiving an intake is neither membership approval nor government approval. PDAO registration must never create a `MembershipApplication`, `Member`, program application, assistance release or PA entry.

Reuse existing Django apps, services, MySQL, templates, shared styles and eight Admin groups. Add the records below to the membership domain; do not introduce a generic case engine, separate authentication system or new login roles. Existing UUID membership references, issued program references and control numbers remain immutable. Ordinary program identity/photo verification, program PDAO approval, selection, publication and actual releases remain separate and unchanged.

Phase 2B excludes public tracking, public post-submission editing/recovery, member accounts, SMS/email/PIN/OTP, QR tracking, government APIs/transmission/issuance, appointments without actual assignment, referral tickets, RSVP, new evidence measures and automatic EWAF calculation. No intake state enters an EWAF pool. Initial-assessment information remains a declaration until an existing authorized source service accepts it in its proper workflow.

## 2. Proposed additive records

Names are review labels, not generated model or migration files. Use explicit typed fields for identity/state/relations and a strictly allowlisted, versioned JSON schema for submitted form snapshots and typed action payloads. Reject unknown keys; no arbitrary model-field assignment or client-supplied trusted state. Keep the existing `MembershipApplication` and `Member` schemas unchanged.

| Record | Proposed persisted data | Constraints and lifecycle |
|---|---|---|
| `RegistrationIntake` | Internal key; category `association`/`pdao`; immutable external reference; original channel `online`/`printed`/`walk_in`; received timestamp; state; integer version; current revision number; form/checklist/privacy version identifiers and digests; request key and canonical accepted-payload digest; optional submission-context link; optional existing membership-application link; handoff revision/finding pointers | Unique external reference and request key; one-to-one membership link, nullable and Association-only. Online creation requires its bound context. No Member/program/EWAF FK. State/category compatibility enforced in service and DB constraints. List indexes category/state/received time; exact reference uses its unique index. Retain original channel; later paper presentation is an action, not a channel rewrite. |
| `RegistrationRevision` | Intake FK; revision number and predecessor; schema version; validated form data; approved checklist/instructions snapshot; author staff ID or submission-context ID; original capture channel; timestamp and correction reason | Unique `(intake, revision_number)`; original revision immutable. Corrections append and increment intake version transactionally. References to predecessor must belong to the same intake. Never overwrite an original application or its attachments. |
| `RegistrationAttachment` | Revision FK; approved requirement key and chosen alternative; random private storage key; original filename retained privately; MIME/size/digest; uploader context/actor and time; optional replaced-attachment pointer | One accepted file per approved slot per revision unless a separately approved form explicitly defines more. Unknown/repeated slots rejected. Same-intake predecessor checks. No public URL, physical-item placeholder or executable preview. A later revision can reference unchanged prior evidence explicitly; replacement does not erase it. |
| `RegistrationAction` | Intake FK; version before/after where mutating; action code; actor ID and retained label or bound submit context; time; reason; revision/finding/attachment pointers; typed payload | Append-only service writes; no editable audit form or generic delete. Mutation and its audit commit together. Onsite findings and PDAO forwarding facts are typed actions, avoiding separate redundant tables. Restricted read/export/download actions have actor/time/object/outcome audits without copying the form into logs. Failed-attempt counters/security logs are separate and minimal. |
| `RegistrationSubmissionContext` | Opaque internal context ID; server-side session binding digest; request key; category and form-policy version; issued/expiry/revocation timestamps; accepted intake relation through the intake | No name, documents or applicant draft stored here. At most one accepted intake for a context. Session binding and context must both match before completed-form delivery or retry response. Not a Member account, tracking credential or identifier-based recovery service. Security lifetimes and attempt limits remain unset until D06. |

Cross-row consistency, immutable references, current-revision checks and append-only history need transactional services as well as DB constraints; do not claim a simple CHECK can validate related rows. Use existing private storage and file validators without changing old attachment ownership. Intake/revision/attachment links are protected against casual cascading deletion. An approved disposal process must explicitly handle them; unrestricted Admin bulk deletion is excluded.

Approved form/checklist/privacy documents should be versioned inputs with digests and retained snapshots. A runtime gate must reject submission when a required approved version or security parameter is absent, inconsistent or superseded. Merely entering an approval date in the UI must not grant operational authority. How approval evidence is supplied and reviewed is D10/D11, not a new self-approving policy editor.

## 3. Minimum fields and supporting documents

The source confirms document lists, **not a complete approved online fieldset**. Do not treat the current onsite ModelForm or unseen external government form as that fieldset. D01 requires field-by-field client review, including purpose, requiredness, length, permitted values, correction and retention. The following is the proposed minimum to review, not a claim about PDAO Form 4.0's contents.

| Data | Association candidate minimum | PDAO candidate minimum / boundary |
|---|---|---|
| Registration category, channel, reference, timestamps, state and policy version | Set by server; applicant cannot choose a trusted state or supplied reference | Same; separate endpoint/category allowlist |
| Applicant name | Required declared full name, preserving spelling/diacritics; structured name collected only where approved form needs it | Same proposed core identity field, pending approved PDAO form mapping |
| Birthdate | Required valid date not in the future | Same proposed core field; not a derived eligibility or EWAF decision |
| Residence | Required declared address within approved length; no invented automated residency determination | Same; checklist proof and review remain separate |
| Contact | Proposed optional contact number with an explicit no-contact/onsite-follow-up route; no invented value to satisfy old form validation | Same. D01 must approve reachability expectations; no messaging service follows from retaining contact data |
| Privacy and accuracy declaration | Versioned notice shown before submission and reviewed confirmation of submitted information; record acknowledgement | Same; acknowledgement is not an invented legal processing ground or waiver. Wording/ground require D10 |
| Disability/initial-assessment information | Collect only separately approved minimum declarations; otherwise collect applicable profile information onsite. No trusted evidence, score or income amount on this new form by default | Only fields necessary for the approved PDAO form/process; do not separately transcribe all medical certificate text without approved need |
| Representative/assisted submission | Applicant remains record subject. Staff-assisted capture records actual staff actor. Caregiver/representative authority and fields require D01/D03; relationship alone grants no private access | Same, with separately approved PDAO authority; do not infer it from membership practices |
| Association control number, government ID, member identifier | Not required from a first-time online applicant. Staff must resolve the legitimate existing/new control-number contract before handoff (D04). No dummy number | No Association control number. Do not require a government ID for a first-time application. Renewal identity/surrender fields remain unavailable unless separately approved |
| Email, household income, program-match fields, scores, selection | No new mandatory email; no Household Monthly Income, replacement ordinary matching or calculation fields | Same exclusions |

The old onsite form requires additional structured profile fields and a control number. It also treats contact/dependents/disability information according to its existing validation. An incomplete pending submission may be retained, but handoff must wait until staff can produce a valid, truthful existing onsite form under approved procedures. Do not fill blanks with zero, “unknown,” false verification or a synthetic identifier. Hidden legacy `monthly_income`/employment fields are not authorization to collect new Household Monthly Income. The approved mapping must preserve legacy field meanings and show which fields are declared versus independently reviewed.

Output is the **completed submitted pending-intake form**, displaying category, revision and pending status. It may be called an official completed Association/PDAO form only after D01 approves the full field mapping and rendition. A short preliminary intake must not be represented as a complete government form. Print/save/download must preserve the submitted revision and clear mandatory onsite instructions.

**D02 proposal:** permitted pre-uploads are optional until onsite review; this reduces inaccessible upload barriers without waiving any onsite item. The client must decide required online slots versus onsite-only collection before activation. If a required document cannot be supplied, keep the case in a truthful needs-information state using an approved assisted route; do not silently accept an unapproved alternative. Physical handling, accessibility alternatives and validity periods are distinct decisions, not inferred from file type acceptance.

Reuse existing PDF/JPG/JPEG/PNG signature/MIME/extension checks, nonempty checks and portrait validation. Current code defaults are 5 MiB/file and 20 MiB total; portraits are limited to 25 million pixels. These are inspected code defaults, not asserted effective working settings or newly approved online limits. D11 must ratify or explicitly bound online limits, field/file count and attempts without changing unrelated settings. Header validation is not malware scanning or proof of document authenticity.

## 4. Proposed state and review contract

Keep existing membership `pending/approved/rejected` values unchanged. New processing state codes below are distinct from membership decision and government status. No arbitrary status dropdown may bypass a transition's service checks.

| Transition | Required facts, action and authority |
|---|---|
| No record → `received` | Accepted validation, active approved category/policy/gate, bound request, unique reference, revision 1, attachments and submission audit committed; no Member or legacy membership row |
| `received` → `under_review` | Category-scoped staff review permission; actor/time and current version |
| `under_review` → `needs_information` | Specific private findings and approved actionable correction guidance; no inferred rejection/deadline |
| `needs_information` → `under_review` | Staff records a new correction revision, reason/source and preserved originals; onsite or other approved assisted channel only in 2B |
| `under_review` → `ready_for_onsite` | Preliminary completeness check against the retained policy; label says onsite verification is still required. No automatic appointment |
| `ready_for_onsite` or `under_review` → `onsite_review` | Applicant actually presents onsite, or a representative uses an explicitly approved authority route. Direct walk-in may reach this step without a readiness message |
| `onsite_review` → `needs_information` | Actual missing/inconsistent evidence; retain findings, no invented alternative or false pass |
| Association `onsite_review` → `membership_handoff` | All approved onsite findings, valid profile/control-number mapping, no unresolved identity/cross-channel conflict, current revision and permissions; existing submission service atomically creates/links the one pending membership application |
| Association after handoff | Existing membership status is the decision source of truth. Render “Membership review pending,” “Membership approved” or “Membership rejected” from that linked record; do not maintain a second editable decision/status copy |
| PDAO `onsite_review` → `ready_for_forwarding` | IQ-09/16 authority plus approved identity/checklist findings and designated staff sign-off; readiness is not transmission or government approval |
| PDAO `ready_for_forwarding` → `forwarded` | Authorized manual transfer actually occurred; record recipient/process authority, actual date/time, actor and permitted private evidence. No automatic sending, fake status callback or government decision |

Before handoff/forwarding, corrections invalidate readiness/onsite acceptance tied to older revision fields or evidence and return to review. Store the earlier finding unchanged and require a fresh version-bound finding; do not merely change its date. One staff update succeeds against the expected version; stale/concurrent updates are rejected for reload without overwriting another action.

No withdrawal, duplicate-closure decision, expiry, automatic rejection, reopening, replacement of finalized member data or reversal of forwarding is inferred. D14 governs any future terminal remedy. An already-linked membership correction must use a demonstrably safe authorized service; if the current service does not support it, retain a review request and block the mutation. Do not unlink/recreate a Member or quietly edit copied source data.

### Onsite findings under OQ-27

1. Authorized staff locate the existing reference first and confirm the appropriate category. A printed online form is evidence presented for the same record, not a new application. A blank print/walk-in intake receives a new pending record only after approved duplicate review; legacy walk-in workflow remains available and unchanged.
2. Staff perform the approved identity/representative procedure and compare the retained revision with presented information. Name/contact similarity or possession of the printout alone cannot establish identity. Do not invent new identifying questions, document alternatives or identity-match fields for program applications.
3. For each required item record the actual document alternative, original/copy/physical method permitted by policy, observed/received date, reviewer, finding and reason. Proposed item findings are `not_reviewed`, `sighted`, `missing`, `requires_clarification`; a policy-accepted finding must additionally identify the approved basis. Sighted is not automatically authentic, current or accepted.
4. Record the physical envelope independently. Record a paper document's observation without an upload when the approved policy permits paper-only retention. If old configured required-file guards cannot represent that treatment, conversion stays blocked pending a reviewed compatible design; do not upload placeholders or disable guards.
5. Keep Association checklist completeness separate from existing manual PRPWD verification. Only its authorized service records actual registry review through the configured external link. A PDAO-ID prerequisite is still unconfirmed; lack of a truthful path through the preserved manual review is a blocked case, not authority to fabricate a positive result.
6. Readiness is derived from current accepted findings and unresolved-case checks. Required original/copy rules, permitted scan retention, validity/expiry/reverification, correction/return/completion steps and any new alternatives require D02/D03. No arbitrary review deadline or sampling rate is proposed.

### Safe membership handoff and the existing writer

The proposed extension calls existing `submit_application`, `record_verification` and `decide_application` with a real authorized staff actor and valid existing forms/tokens. Preserve their `membership_writer` wrappers, capability checks, terms/authority/source locks, source freshness, required files, PRPWD, version/reason checks and native audit expectations. Do not pass anonymous data through a fabricated staff account or write `Member` directly.

The enrolled writer calls a top-level durable boundary. **Do not surround the three services with one new outer transaction.** Propose narrowly scoped optional intake integration inside the existing non-EWAF membership service bodies: validate/lock the linked intake after the existing required locks, and write its link/finding audit inside the service's own transaction. Unlinked legacy calls retain their exact behavior. Additional intake audit rows use `RegistrationAction`, not extra native `MembershipEvent` rows that would violate the protected wrapper's expected audit count.

Handoff uses a stable request key tied to the accepted intake/revision and policy. Its existing membership submission, one-to-one intake link and handoff action must succeed together or roll back. A retry returns the same linked pending membership record after permission/context checks. The stored handoff revision/finding remains immutable. Subsequent manual verification and decision are separate top-level operations; failure leaves a truthful pending case, never a simulated completed conversion.

The existing decision service needs a linked-intake guard **inside its transaction**, so every existing/new route that approves a linked case rechecks approved onsite findings, accepted revision, unresolved conflicts and the actor's extra intake permission. A hidden button or a check only in the new view is insufficient. Ordinary unlinked membership processing must stay unchanged. Acquire new intake locks only after the existing writer's locks; test the resulting lock order in both ordinary and enrolled disposable modes. Do not hold an intake transaction while entering a writer that requires top-level entry.

Linking must not create a permission bypass through the old UUID. For linked records, legacy list/detail/history/export and document paths must apply the approved intake scope **as well as** their existing permissions; document access needs both applicable document grants. Filter inaccessible linked cases before list counts/results and guard direct requests before disclosure. Verification/decision requests also recheck the linked intake authority. Preserve old permissions and behavior for unlinked historical cases. This small conditional integration belongs to D09/D12's reviewed scope; a new private intake viewer alone cannot secure its later copied legacy record.

This is an approved-design candidate, not demonstrated safe composition. D12 requires a compatibility proof covering audits, storage failure and concurrency. If the integration needs any protected writer/engine change, stop that path and retain the intake as pending. Never use non-enrolled mode as a workaround for a failing enrolled-mode test.

## 5. IQ-10 references, retries and duplicates

**Recommended new namespace proposal (D05):** `AMR-<canonical UUIDv4>` for Association registration and `PIR-<canonical UUIDv4>` for PDAO assistance. Each is 40 ASCII characters, allocated server-side from a cryptographically suitable UUIDv4 generator, backed by a unique constraint, immutable and non-identifying. Internal row keys and any later legacy membership UUID remain distinct. No reused program sequence, birthdate, name, ID fragment or manually entered rank. Never alter issued legacy references.

On a unique-reference collision, allocate again under a bounded retry policy; fail safely without acceptance if exhausted. Collision handling must distinguish a reference collision from a duplicate request-key conflict. The numeric collision/attempt limits belong to the reviewed technical configuration, not an invented institutional policy. Canonical case/format normalization is exact; partial reference input must not broaden staff lookup. Keep the existing raw UUID parser and program reference rules intact.

**Request contract:** issue a server-side request key bound to the initiating session, category and approved form version. Canonicalize only allowed field representations; hash accepted validated content plus ordered attachment digests and policy version. Store the request key, payload digest and intake atomically. Same key + same bound context + same accepted payload returns the same receipt; same key + changed payload returns a conflict without overwriting the original. Another session/staff identity cannot use the key to recover private data. CSRF applies independently. Pending simultaneous requests serialize through unique constraints/locks; an IntegrityError is handled outside the failed atomic block before a scoped re-read. No success receipt before commit.

File storage is not transactional with MySQL. Stage/write private objects with unpredictable keys; validate before acceptance; record the storage handles needed for cleanup; commit intake/revision/attachment/audit only when required writes succeed. Rollback removes uncommitted files. Cleanup failure is a restricted operational incident with a retriable orphan record/process, not a hidden success or public URL. Define a testable recovery procedure under D11; no new background calculation/notification infrastructure is implied.

**Duplicate people are different from duplicate requests.** Only an accepted request replay is automatically deduplicated. A second request key, matching name/contact/date, or shared household never silently merges people, replaces evidence, or grants membership. Authorized staff see possible matches within their category permissions and record review findings. Actual same-person/cross-channel matching must follow D03/D07. Link a presented online reference after identity review; if unavailable, use approved staff-assisted recovery only. Do not introduce public search by identity data or recovery by reference alone. Ambiguous cases remain pending. Membership creation still faces the existing one-to-one application and unique control-number guards; those do not prove every identity duplicate is detected.

## 6. Completed-form access and Phase 2A reuse

After successful submission, the same authorized submission interaction may display the receipt and completed original form for save/print/download. Propose a server-side session-bound output capability scoped to that intake and revision, checked on every request against the accepted context, expiry/revocation and category gate. Reference possession is insufficient. The capability is not put in query strings, a QR, browser persistent storage or general logs. A signed reference alone is also insufficient. A later fresh session receives generic denial and approved Help Desk instructions; no automatic PIN, OTP, account or email recovery.

D06 must specify lifetime, shared-device finish/clear action, warnings/extensions without privilege escalation, attempt counters and revocation before this route can be enabled. No lifetime is copied from the existing onsite form's one-day signed token. The proposed output capability gives access only to the submitted form/receipt, not attachment downloads, staff findings, later corrections, decisions or tracking. No public attachment endpoint is added. Saved/printed copies are under the applicant's control; show a plain shared-device privacy reminder without implying the system can retract downloaded files.

Use authenticated Members intake lists with reference/type/submission date/processing state, a dedicated labeled exact search and a canonical private detail page. Reuse Phase 2A's accessible search/result presentation and permission-first behavior. Route new prefixes to category-scoped intake lookup; retain old raw UUID lookup and existing detail/document routes. Do not feed new references into the old UUID-only query or expose a universal public dispatcher. Staff select a record; the reference does not broaden their category or document rights.

Authenticated errors: malformed reference can receive a field error after authorization; well-formed absent or inaccessible references share a generic unavailable response within the searched scope. Unauthorized users cannot infer existence through results, downloads, exports, history or differing error content. Repeated search/GET/HEAD must not create an intake/member or change state; deliberate protected downloads may add the existing required audit event. Mutations use CSRF-protected POST and expected-version checks.

Optional QR is **omitted from the initial 2B proposal**. Text references and printouts meet the retrieval objective. If later approved, a reference-only QR remains an identifier, cannot encode secrets/PII or authorize private access, and must not activate public tracking. IQ-03 remains open independently.

## 7. Permissions and Admin placement

Use active authenticated staff plus `accounts.access_dashboard` and category-specific capabilities. Proposed capabilities below are action labels; final codenames/assignments need D09/D12. Do not make existing “Admin,” superuser status or a view permission an institutional grant of PDAO power.

| Capability | Authorized operation / additional boundary |
|---|---|
| View Association intake / View PDAO intake | List/search and approved private form fields in its category only; PDAO requires approved operational authority |
| View/download Association intake documents / PDAO intake documents | Separate category-specific sensitive-document permission plus view capability; recheck every access, audit before delivery |
| Encode assisted intake / Record correction, separately by category | Actual authorized staff capture/revision; no alteration of original, final case or other category |
| Record Association onsite findings / PDAO onsite findings | Only approved checklist and identity procedure; cannot set manual PRPWD success or membership/government decision |
| Handoff Association intake | Intake view + onsite/handoff authority and existing `membership.encode_membershipapplication`; version-bound accepted findings |
| Manual PRPWD / membership decision | Existing `membership.verify_membershipapplication` or `membership.decide_membershipapplication`, existing dashboard/membership view requirements and new linked-intake checks; no automatic permission grant |
| Record PDAO forwarding fact | PDAO view plus specifically assigned forwarding authority; current approved recipient/process and actual-transfer evidence required |
| Read intake history / print completed form | Category view and separately approved history/export scope as needed; no generic export endpoint with broader rights |

Assignments must name responsible existing staff functions, approving authority, scope and revocation process. No new Treasurer/Officer/Auditor/member login role. Decide any separation-of-duty requirement explicitly; this proposal does not invent a two-person rule. Recheck active account/permissions at the transaction boundary and protected-file request, including changes during an open form. Test permission revocation races; a cached page/link is not continuing authority.

**Members owns** registration categories, canonical detail, onsite findings, corrections, membership handoff/decision links and PDAO facts, as integrated §6.9 specifies. **Applications & Verification retains** program applications and its existing verification tools. It may link to a permitted Members record if approved, but owns no duplicate registration workflow. Referral tickets and information/evaluation reviews in that module remain later phases. **Reports & Exports** may link to the same permission-checked completed-form renderer, without new export families. **Administration** holds permission assignment and protected audit responsibility. No new sidebar group or renamed group. Dashboard shortcuts are optional links, not new statistics. Seven Public destinations remain in order; Resources & Help belongs to Phase 4.

## 8. Privacy, security, retention and accessibility

- Enforce category gates in URLs/views/services and direct file/export actions, not just buttons. Separate public submission, submission-context output, staff review and PDAO forwarding gates; disabled dependencies fail closed. A schema or hidden draft page never activates a workflow.
- Allowlist fields for each audience. Staff details are not reused as a public serializer. No public lists, confidential reasons, forms, documents, full IDs, ranks or expanded result masks. Preserve existing initials/last-four allowlists. Even a reference should be excluded from routine public analytics/referrer logs where feasible; never log request bodies or sensitive filenames.
- Private randomized storage, no unrestricted `/media/`, authorization before open, attachment disposition, no-store/nosniff and sandbox for permitted previews. Escape filenames/content; no remote URL fetch or executable uploads. CSRF, bounded field/file/body sizes, request/attempt quotas, session expiry and abuse handling are required before public use. D11 records the limits and enforcement storage; disabled/unconfigured protections must block activation. No claim of malware scanning without an actual approved scanner or equivalent reviewed handling plan.
- Audit transitions and corrections with actor, time, reason, version, category and protected provenance. Record anonymous submit through its context without pretending it was authenticated identity. Changes/audits are transactional; failed auditing prevents state change or protected delivery. Keep unsuccessful-attempt logs minimal and separately access-controlled. Bound counters without revealing whether a reference exists.
- D10 must approve processing purposes/grounds, privacy wording, recipients, access assignments and retention schedules separately for pending/rejected/linked/forwarded forms, attachments, physical review records, actions, contexts/attempts and backups. Include holds, authorized disposal, failed-upload cleanup and retained provenance. No arbitrary expiry, indefinite-retention promise, automatic deletion or live retention job is introduced. Do not remove a file still needed by the linked legacy application's required-document/history rules. Any copied legacy evidence needs explicit source/digest mapping and independent private file lifecycle.
- Onscreen review before submit; fieldset/legend and explicit labels; required/optional markers; keyboard focus and no traps; error summary linked to invalid fields; screen-reader status messages; adequate contrast, text resizing/reflow, readable receipt and semantic print output. Choose a readable HTML print/save flow using existing tooling first; any PDF claim requires accessible verified output and dependency review. No forced popup or hardware kiosk.
- Retain text/reference entry and assisted print/walk-in routes; no mandatory QR/scanner, drag gesture or inaccessible upload control. Provide approved document alternatives only. User-controlled reading aloud must have start/stop controls, not autoplay or transmit private text to an unapproved external service; select-and-read/screen-reader compatibility remains essential. Reading assistance does not reveal another case or bypass evidence rules. Timeout warnings/extensions require a safe, approved context design.
- Test representative keyboard, screen-reader, zoom/mobile, error/retry, shared-device and print journeys with synthetic data; record untested combinations. Previous Phase 2A browser evidence does not establish 2B accessibility or WCAG certification. Institutional UAT remains pending until sessions actually occur.

No security or accessibility convenience changes EWAF criteria, verified dates, source freshness, complete-pool blocking, exact ties, ranks, history, human decision/capacity, publication or release/PA semantics. If a dependent action needs a protected contract change, it remains unavailable.
