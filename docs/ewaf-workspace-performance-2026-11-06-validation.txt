EWAF tab and applicant switching performance - 2026-11-06

Owner request
Speed up the EWAF tab and switching an applicant on the left to show inputs on
the right.

Measured cause
Every row click fetched and rendered the entire workspace. A 12-applicant page
performed three complete inventory inspections (preview, generation readiness,
saved-ranking freshness), with repeated source/evidence reads. Policy validation
also rebuilt the same choice definitions for every individual choice.

Implemented
- Pre-render applicant panels for only the displayed ranked/unranked pages and
  the explicitly selected applicant. Inert HTML templates hold these cards in
  this private page's memory. Clicking a loaded row switches the panel, highlight,
  accessible selection state and URL locally, without a network request.
- Different rankings, filter results and unloaded applicants still use the
  permission-checked server route. Superseded requests are aborted and their
  responses cannot replace a newer local selection. No localStorage, browser
  database, cross-user cache or persisted applicant-data cache was added.
- GET workspace and program-preview requests reuse matching inventories within
  one existing terms-lock transaction. The request-local cache distinguishes
  program/application/member versions, configuration digest, assessment cutoff,
  evaluation date and timezone. Each caller gets an independent deep copy.
  The cache is discarded even on error. POST generation/selection and all
  callers outside these GET scopes continue to execute fresh inspections.
- Authority, source observation, evidence checks, retained-run validation and
  decision services remain in place. Rendering additional cards does not select
  anyone. A stale form is still rejected by the server after records change.
- Reuse the constructed policy-choice definitions inside each validation/catalog
  loop. This removes repeated copies without changing choices or findings.
